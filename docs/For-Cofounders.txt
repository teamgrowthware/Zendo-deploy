What Zendo is

Zendo is one app that runs the Zendo blockchain, the ZendoCoin wallet, and a meme coin launchpad together. People hold and send ZendoCoin, stake it on the chain, and create and trade meme coins from the same app, while $ZCoin is the coin that pays for those actions.

There are two ledgers, and they stay separate until the bridge. The app chain is zendo-1. Balances there live in the wallet that created them, on the machine that runs the node. $ZCoin on Polygon is the public coin outside the app. Holding coins in the app does not put tokens in a Polygon wallet. Staking rewards are new coins on zendo-1 only. They do not mint Polygon $ZCoin. Polygon supply stays 1,000,000,000. The bridge is the only meeting point, and it locks coins the vault already holds and releases those same coins. It does not mint.

Vesting is four years. The cliff is 120 days. Nothing is released during the cliff, including on the cliff day. After that, each founder unlocks 25 percent of that founder's own allocation at each 365-day anniversary. Year 1 is Louis 50,000,000, Prabhat 12,500,000, and Pratyaksh 12,500,000. Year 2 is 50 percent cumulative. Year 3 is 75 percent. Year 4 is 100 percent. Each founder calls release() and can take only their own coins. There is no admin key and no second mint. The Polygon clock starts at the deploy block. The app clock starts the first time the app is served on a public HTTPS host.

The contract we deploy for the public coin is ZendoCoinLaunch. It creates the token, creates the vesting contract, sends 300,000,000 to vesting, and sends 700,000,000 to the public recipient we paste at deploy. ZendoBridge is a separate contract. The launch contract does not deploy the bridge.

What changed

The app ledger no longer writes a single state.json file over itself. Balances, documents, and replay guards sit in data/zendo.sqlite. Writes are transactions. A concurrent test of four workers crediting the same balance 25 times each committed all 100 credits. If an old state.json is present on first boot, it is imported once and renamed. The same table layout is written down for Cloudflare D1 in cloudflare/d1-schema.sql. Key-value storage is the wrong place for balances. One process still owns the chain. A serverless host that wipes the disk would forget the wallets.

A Cloudflare edge check now sits in front of the API shape we care about. HTTPS is required. A health check reports that the ledger is SQLite and that the request arrived with TLS. Mutating API calls must be JSON and stay under the size cap. Withdrawals, deposits, and transfers are checked for address shape and a positive amount before anything is forwarded. On the preview host this answered with a Cloudflare ray. Our own domain and our own D1 database are not connected yet.

Polygon reads go through QUICKNODE_POLYGON_RPC_URL when that is set, and otherwise through POLYGON_RPC_URL. A check script pulled a Polygon mainnet block header and a transaction receipt. Chain id was 137. The QuickNode URL is not set on this preview, so the live watcher is not using our account yet. A public fallback was used only to prove the read path.

The bridge watcher is in the app. When a bridge address and an RPC are set, it scans Locked events, waits for confirmations, and credits the matching znd1 wallet if the vault can pay. The same lock cannot be credited twice. A withdrawal signs a voucher and will not sign the same nonce again. A full lock and release was run on a local chain that reported chain id 137. On this preview the watcher is idle, because the bridge address and the signing key are not set. A withdrawal attempt on that idle node refuses and leaves the coins in the wallet.

Where we are

We can show the app, create a wallet, send, stake, launch a meme coin, and trade it on this node. The Polygon contracts match the three of us and the vesting rules. They have not been broadcast to Polygon mainnet. The bridge code can lock and release on a test chain. It is not watching mainnet. The preview address is a temporary tunnel. It will die. Phone download buttons that point at it have to be pointed at our real domain after we have one.

What is left before the public

1. Put Zendo on one machine we control, with data/zendo.sqlite on a disk that survives restarts. Point our Cloudflare domain at that one process over HTTPS. One replica. The quick preview hostname is not the launch.

2. Set QUICKNODE_POLYGON_RPC_URL on that machine so the node reads Polygon through our endpoint.

3. Deploy ZendoCoinLaunch on Polygon mainnet, chain id 137. Remix or the deploy script. The only cost is Polygon gas in POL. In publicRecipient, paste the wallet that should receive the 700,000,000 public coins. Deploy ZendoCoinLaunch only. Do not deploy a generic token drop. That would skip vesting.

4. After the coin exists, set ZENDO_POLYGON_BRIDGE to the bridge contract and set ZENDO_BRIDGE_PRIVATE_KEY on the server, mode 0600, never in git. Until both are set, withdrawals stay refused and coins stay in the app wallet.

5. Change the seeded operator password and PIN before anyone else can reach the node. Password reset links are shown in the app. There is no mail server.

6. After the domain is live, point the phone download buttons at that HTTPS host. A tap has to be a plain link to the absolute https address, opened at the top of Chrome, with the file served as application/zip and the name ZendoApp2026.zip. That is the pattern that saves on Android.
