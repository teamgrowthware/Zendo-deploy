Build on zendo-1

The TypeScript client talks to this node. JSON-RPC covers reads. Writes go through the signed-in wallet routes.

TypeScript

Open the learn page
import { createZendoClient } from "./lib/sdk";

const zendo = createZendoClient("http://127.0.0.1:38471");
await zendo.connectNode();
await zendo.getBalance("znd1...", "ZCOIN");
await zendo.estimateGas();
await zendo.sendTransaction({ to: "znd1...", amount: "1", token: "ZCOIN" });
await zendo.deployContract({ name: "Pond Frog", symbol: "FROG", description: "A frog on-chain.", emoji: "🐸", hue: 88 });
await zendo.callContract({ mint, method: "trade", side: "buy", amount: "0.5" });
await zendo.stakeTokens({ validatorId, amount: "10" });
await zendo.voteProposal(proposalId, true);
const stop = zendo.subscribeEvents((status) => console.log(status.height));

JSON-RPC lives at POST /api/rpc. Methods: zendo_chainId, zendo_blockNumber, zendo_getBalance, zendo_getBlockByHeight, zendo_getTransactionByHash, zendo_estimateGas, zendo_call. Chain reads and writes have no per-minute cap. Live blocks stream from GET /api/stream as event: block.

Kotlin and Swift clients in sdk/ call the same HTTP routes. Network parameters, including gas and the validator set, are in zendo-blockchain.toml.

The Rust process in node/ keeps its own blocks. It learns peers by exchanging listen addresses, prefers a lower measured round trip, and will switch to a longer chain when the shared ancestor is at or above the finalized height. A second validator can join that same genesis before the first block and keep depth finality moving while the other signer is quiet. Vote finality still waits for a quorum. A --region label rides along in the hello message. Its RPC, bound to localhost, adds zendo_consensus, zendo_peers, zendo_getCode, and zendo_getStorage. The explorer page at /explorer/consensus polls the peer and fork methods through GET /api/node.

That process also executes contract bytecode. Deploy by sending data to the zero address. Call by sending a transaction to the deployed address. The deploying account can replace the code with a payload that starts with A1, or restore the previous body with A2. zendo_call runs the same code without writing state. zendo_governance reads a governance contract's tallies, and zendo_staking lists bonds held at the stake address. Opcodes cover push, arithmetic, storage, logs, jumps, caller, balance, calldata, native sends, and a depth-limited call that forwards one selector and one argument. Gas is the fee. A revert rolls the storage back and burns the gas used. node/src/contracts.rs builds a token, a cliff vesting schedule, a constant-product curve, a one-ballot governance contract, an NFT, and an identity registry whose reader calls the registry. Those programs live on the Rust node. The website launchpad, vesting, and governance still settle in the TypeScript ledger.

Simultaneous transactions join one ordered batch and share one commit. Promoted launchpad slots and the optional MEV skim are the paid surfaces. MEV here is a config switch that adds 5 basis points to the protocol side of a trade. It does not reorder anyone else's transactions on a public mempool, because this node is the only producer.

Nested reads are POST /api/graphql. The live query returns chain height, the latest prices, recent trades, and the launchpad book in one response. The same feed is pushed on the stream as event: market. Prices and the book are cached for one second. Set ZENDO_REDIS_URL to a Valkey or Redis URL and that cache is shared, including sign-in and PIN attempt counts. The signed session cookie stays the session. gRPC listens only when ZENDO_GRPC_PORT is set. proto/zendo.proto is the contract. Each send writes a debit and a credit into the journal and the transfers table in the same database transaction. A TigerBeetle cluster is used only when TIGERBEETLE_ADDRESSES is set on a machine that is already running TigerBeetle. This app does not start that cluster. The screens still use the existing routes.

The white paper is the release note for supply, vesting, and fees. npm run whitepaper reprints public/whitepaper.pdf from docs/whitepaper-body.html using the version in package.json.

A chain you host yourself. Keys stay in the wallet that created them. The ledger stays on disk.
